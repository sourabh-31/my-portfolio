Web fonts can have a surprisingly large impact on how fast a page feels. A font may only be 10 to 30 KB, but the browser still has to discover it, connect to its origin, download it, parse it, and use it before the final typography appears. Multiply that across several families and weights, and fonts quietly become one of the heaviest parts of the critical rendering path.

The good news is that font optimization doesn't need to be complicated. You don't need to eliminate every font or obsess over shaving a few hundred bytes off a file. What you need is simpler: make sure the browser receives only the fonts it needs, in the format it needs, at the time it needs them.

Here's a practical 9-step process for getting there.

---

## 1. Use WOFF2

For modern websites, start with WOFF2. It compresses better than the older WOFF format and is supported by every browser you're likely to care about. Unless you have a specific compatibility requirement, there's little reason to ship WOFF as your primary format, let alone TTF or OTF.

A typical setup looks like this:

```text
fonts/
├── geist-400.woff2
├── geist-700.woff2
└── geist-mono-400.woff2
```

Not this:

```text
geist-400.ttf
geist-400.otf
geist-400.woff
geist-400.woff2
```

But the format is only half the story. A well-compressed font you don't actually need is still unnecessary bytes on the wire.

---

## 2. Ship only the weights and styles you use

Font families often ship with a full range of weights:

```text
100  Thin
200  Extra Light
300  Light
400  Regular
500  Medium
600  Semi Bold
700  Bold
800  Extra Bold
900  Black
```

Your design almost certainly doesn't use all nine. If your site only ever renders `400` and `700`, there's no reason to define anything else:

```css
@font-face {
  font-family: "Geist";
  src: url("/fonts/geist-400.woff2") format("woff2");
  font-weight: 400;
  font-style: normal;
}

@font-face {
  font-family: "Geist";
  src: url("/fonts/geist-700.woff2") format("woff2");
  font-weight: 700;
  font-style: normal;
}
```

The same logic applies to styles. If you never use italics, don't ship an italic file just because the family happens to include one. The browser only downloads what your CSS asks for, so every unused `@font-face` declaration you remove is a request that never gets made.

---

## 3. Choose static or variable fonts based on actual usage

Variable fonts are useful, but they aren't automatically faster, and that's worth internalizing before you reach for one by default.

A static setup might be three separate files:

```text
Geist-400.woff2
Geist-500.woff2
Geist-700.woff2
```

A variable font collapses that into one file, with the weight controlled in CSS:

```css
@font-face {
  font-family: "Geist";
  src: url("/fonts/geist-variable.woff2") format("woff2");
  font-weight: 100 900;
  font-style: normal;
}
```

That single file is convenient, but the browser still downloads the whole thing. It doesn't fetch only the `400` or `700` slice of it. So the right comparison is the actual file sizes:

```text
Static (400 + 700):    12 KB + 13 KB = 25 KB
Variable (100–900):    48 KB
```

If a site only needs two weights, the static files clearly win here. Flip it around and the variable font wins when a design genuinely uses five or six weights across a range, since one 48 KB file can easily beat five or six separate downloads. The point isn't that one approach is better. It's that the decision should follow from what your design actually uses, not from which format feels newer.

---

## 4. Subset your fonts

A font file can contain thousands of glyphs, often covering scripts you'll never render: Latin Extended, Greek, Cyrillic, Vietnamese, various symbol sets. If your site only needs basic Latin characters, all of that extra coverage is dead weight.

A subsetted font strips the file down to only the glyphs you actually need, which is usually a dramatic size reduction for anything targeting a single-language audience. Common subsets you'll see offered by font tools include `latin`, `latin-ext`, `cyrillic`, `greek`, and `vietnamese`. Pick based on the content your site actually serves today, but keep localization plans in mind. If you know you're adding a second language next quarter, it's worth including that subset now rather than re-cutting the font later.

## 5. Define accurate fallback fonts

A custom font isn't guaranteed to be available the instant a page renders. Your fallback stack is what the browser uses in the meantime, so it's worth treating as a real design decision rather than an afterthought:

```css
:root {
  --font-sans: "Geist", system-ui, sans-serif;
  --font-heading: "Satoshi", system-ui, sans-serif;
  --font-mono: "Geist Mono", ui-monospace, monospace;
}
```

A good fallback stack lets text render immediately, before the web font has even started downloading. For a more polished result, pick fallbacks whose metrics are reasonably close to your primary font's. When the fallback and the final font differ a lot in width or line height, swapping between them causes a visible layout shift.

CSS gives you tools to close that gap without changing fonts:

```css
size-adjust: 95%;
ascent-override: 90%;
descent-override: 22%;
line-gap-override: 0%;
```

This is genuinely useful, but it's also a fine-tuning step. Reach for it after you've already cut unnecessary downloads and fixed loading priority, not before.

---

## 6. Choose `font-display` deliberately

`font-display` controls what the browser shows while it's waiting for a web font to arrive. The common values are `auto`, `block`, `swap`, `fallback`, and `optional`.

For most sites, `swap` is a sensible default:

```css
@font-face {
  font-family: "Geist";
  src: url("/fonts/geist-400.woff2") format("woff2");
  font-weight: 400;
  font-style: normal;
  font-display: swap;
}
```

With `swap`, the browser renders text in the fallback font right away and replaces it once the web font loads, so important content is never invisible while it waits.

That said, `swap` isn't the right choice everywhere. For a font that's more of a nice-to-have than essential to the page's identity, `optional` can be a better fit:

```css
@font-face {
  font-family: "Geist Mono";
  src: url("/fonts/geist-mono-400.woff2") format("woff2");
  font-weight: 400;
  font-style: normal;
  font-display: optional;
}
```

Which one you want really comes down to a single question: is this font essential to the page, or is it an enhancement the browser can skip on a slow connection?

---

## 7. Preload only critical fonts

Preloading tells the browser to fetch a resource earlier than it would discover it on its own:

```html
<link
  rel="preload"
  href="/fonts/geist-400.woff2"
  as="font"
  type="font/woff2"
  crossorigin
/>
```

That's genuinely valuable when a font is required to render important above-the-fold content. It's also easy to overdo. Say your page defines seven font variants:

```text
Geist 400, Geist 700
Satoshi 400, Satoshi 500, Satoshi 700
Geist Mono 400, Geist Mono 700
```

Preload all seven and you've told the browser all seven are critical, which means they now compete with your HTML, CSS, and images for bandwidth right when it matters most. A better approach is to look at what's actually visible above the fold, identify the specific weights that content needs, and preload only those. Everything else can load the normal way. In Astro, either the framework's font tooling or an explicit preload hint works for this, as long as you're deliberate about which variants make the list.

The principle worth remembering: preload critical fonts, not every font you own.

---

## 8. Self-host fonts and configure caching

Self-hosting puts you in control of how fonts get delivered, instead of routing every visitor's browser through a third-party font provider first. Serving from your own origin or CDN cuts out that extra hop, and it also hands you control over the subsets you ship, your cache headers, your preload behavior, and how everything gets deployed.

Caching matters especially for static fonts. If your build system generates hashed filenames, something like `/_astro/fonts/4ed3bdac103d467c.woff2`, the filename itself changes whenever the content does. That's exactly the situation where long-lived, immutable caching makes sense:

```http
Cache-Control: public, max-age=31536000, immutable
```

With hashed, immutable assets, a returning visitor reuses the local copy without even asking the server if it's still valid. Compare that to a setup where the browser has to check in every visit and gets back a `304 Not Modified`. A `304` still means the cached copy gets used, but it costs a network round trip to find that out. Immutable caching skips the round trip entirely.

---

## 9. Measure the result

Optimizing each step in isolation only gets you so far. The last step is what confirms whether all of it actually made the page faster, or whether the real bottleneck was somewhere else entirely.

Font performance also doesn't happen in isolation from the rest of the page. Even with every individual file perfectly optimized, fonts still share bandwidth and connections with your HTML, CSS, images, and scripts along the critical path:

```text
DNS → Connection → TLS → HTML → CSS → Critical fonts → Layout → Paint
```

The Network panel in DevTools is where you check this. For each font request, look at its priority, its initiator, the transferred size versus the actual size, and how much time it spent waiting versus downloading. A tiny font that spends most of its time in `Waiting` is telling you something completely different from a large font that spends most of its time actually downloading, and the fix for each is different too.

From the command line, you can pull the same kind of timing data for the page itself:

```bash
curl -s -o /dev/null \
  -w 'TTFB: %{time_starttransfer}s | Total: %{time_total}s\n' \
  https://example.com
```

Run it a handful of times rather than trusting a single request, since network conditions vary enough that one fast or slow run doesn't tell you much on its own:

```bash
for i in {1..10}; do
  curl -s -o /dev/null \
    -w 'TTFB: %{time_starttransfer}s | Total: %{time_total}s\n' \
    https://example.com
done
```

And for a fuller breakdown of where the time actually goes:

```bash
curl -s -o /dev/null \
  -w '\
IP:      %{remote_ip}\n\
Connect: %{time_connect}s\n\
TLS:     %{time_appconnect}s\n\
TTFB:    %{time_starttransfer}s\n\
Total:   %{time_total}s\n' \
  https://example.com
```

Test both a cold load, with no browser cache, and a warm load, with the cache already populated. A site can have an excellent repeat-visit experience while still being slow on the very first one, and you want to know which situation you're actually in before you optimize further.

# A practical font optimization checklist

If you want a simple order to follow:

1. Choose WOFF2
2. Remove unused weights and styles
3. Choose static or variable based on real usage
4. Subset to the glyphs you need
5. Define a solid fallback stack
6. Choose `font-display` deliberately
7. Preload only the critical variants
8. Self-host and configure caching
9. Measure the result

This order matters because it front-loads the work that removes bytes and requests entirely, before moving on to making whatever's left arrive faster.

# Example: a small, intentional font setup

A simple production setup might look like this:

```text
src/
└── assets/
    └── fonts/
        ├── geist-400.woff2
        ├── geist-700.woff2
        ├── satoshi-400.woff2
        ├── satoshi-700.woff2
```

```css
@font-face {
```

Nothing here is complicated. It's just intentional.

# The main idea

Font optimization comes down to doing less work, and doing whatever work remains at the right time. A fast setup is usually the sum of a few things: fewer bytes, fewer unnecessary variants, smaller subsets, good fallbacks, correct loading priority, long-lived caching, and fast delivery, checked against real measurements rather than assumptions.

You don't need a complicated setup. You need to know exactly which fonts your design requires and make the browser's path to those fonts as short as possible.

And once your font files are already small, don't keep compressing them for its own sake. Look at the network waterfall instead. If most of the time is spent waiting on the connection or the server rather than downloading bytes, that's where your next real improvement is hiding.

Don't optimize what looks expensive. Measure what is expensive.
